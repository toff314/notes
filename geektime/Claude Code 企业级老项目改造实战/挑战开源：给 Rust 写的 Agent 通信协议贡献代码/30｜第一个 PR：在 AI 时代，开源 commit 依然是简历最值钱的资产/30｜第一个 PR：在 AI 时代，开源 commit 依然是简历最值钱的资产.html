你好，我是 Robert。

从这一讲开始，我们进入第七部分。回过头看，这门课从第一讲开始，讲的就是同一件事：AI 时代怎么做老项目改造。前面两部分讲了这件事的两种形式。

一种是公司内的老项目。代码是你的、bug 是你的、方向是你定的。你需要在 AI 帮助下读懂、护住、改造一个有几年历史的老代码库。

另一种是基于开源做需求。代码不是你的，但用法是你的。开源项目本质上也是一个老项目，你需要在 AI 帮助下快速摸清它、拆需求、把它当骨架长出你的业务。

这一部分进入第三种形式：挑战开源。代码不是你的，bug 也不是你的，你贡献回去。这同样是老项目改造，只是改造的对象是别人的老项目。

公司内的老项目、基于开源借用别人的成果、贡献开源让你的名字进入社区项目，三种形式背后是同一套方法论：读懂陌生代码、找到改造点、用 AI 高效产出、保住质量。整门课的方法论在这里走完最后一公里。

这一部分三讲。我们先把“为什么”和“怎么开始”讲清楚，再跑通你的第一个 PR。31 讲带你做一个真有难度的 PR，让 AI 当你的 Rust 助教。32 讲把整套动作模板化，给你一份可以反复用的实操脚本。

我自己走过的弯路

讲方法论之前，先讲三段我自己的真实经历。这三段刚好对应一个工程师在开源这件事上常踩的三个坑。

第一个坑是没坚持。很早之前我给 Apache Kafka 提交过 PR。那时候 Kafka 的 review 周期很长，提一个 PR 等几周是常态，我提了两个就停了。但跟我差不多时间提 PR 的另一个人，坚持了四五年，最后成了 Kafka 的 PMC。这件事给我最大的感受是：开源不是技术比赛，是耐心比赛，坚持下来的人拿到的回报还是不错的。

第二个坑是找不到合适的项目。后来有一段时间我特别想再做开源，主要是想给简历增彩，但一直找不到合适的项目。我天天去 GitHub Trending 看推荐，因为自己心里没标准，看完一圈也没相中上手哪个。这个状态持续了好几年。找不到项目这件事本身就是劝退。后来慢慢踩出来一套筛项目的标准，这节课后面会讲。

第三个坑是习惯化前的心理门槛。再后来开源就慢慢变成了我的日常。从一开始“我想给开源做点什么”变成了“开源就是工作的一部分”。一开始觉得开源特别难，这件事对我来说有心理门槛，变成习惯之后就没那么神秘了。简历上“贡献过 XX”这一行，给我自己的信心和职业回报，远超我当初投入的时间。

这三段经历加起来，就是这一讲想跟你讲的最重要的事：开源的难点不在技术，在心理门槛和坚持。AI 时代，这些事都比以前好解决。AI 帮你筛项目，降低“找项目”的门槛；AI 让你在不熟的技术栈上也能有产出，降低“坚持不下来”的门槛。剩下的就是开第一个口子。

为什么 AI 时代开源依然是简历最值钱的资产

很多人会问一个问题：AI 都能写代码了，开源经历还重要吗？

比以前更重要。

AI 让“会写代码”这件事大幅贬值，任何工程师在 AI 辅助下都能产出 80 分的代码。这意味着光说“我熟练使用 Java / Python / Rust” 在简历上越来越没分量，因为 AI 让这条线的下限抬高了，你的熟练和别人的熟练，在面试官眼里没区别。

但开源 commit 不一样。它是公开可验证的工程能力证明，AI 复刻不了。一个人 GitHub 上有 50 个被合并到 Tokio 或 Apache 顶级项目的 commit，面试官能直接点进去看代码、看 review 过程、看跟维护者的讨论。这些东西不可伪造、不可代笔、AI 写不出来。这是 AI 时代留给工程师证明自己的少数几条路之一。

具体的现实收益有三件：

  1. 简历分量。“贡献过 Apache Kafka”、“Tokio 第 N 名贡献者”这些 title 在简历上占的篇幅可能就一行，但它的权重远高于工作经历那几页。因为它是可点击验证的。
  1. 个人影响力。你的代码进了一个有几千 star 的项目，意味着每天不知道有多少工程师都在用你的代码跑生产。这种影响力不靠社交媒体粉丝数撑，靠真实的代码使用量支撑。
  1. 跟核心维护者建立连接。开源圈是个网络，你提一个有质量的 PR，review 它的可能就是这个项目的核心 committer 或者大公司的资深工程师。这种连接不靠饭局、不靠投简历，靠你的代码本身。在我看来，这是开源最被低估的收益。

讲到这里，你可能已经想试试。但开源最难的不是技术，是开第一个口子。

开第一个口子最难

在 AI 出现之前，这件事真的很难，难到让一大批想做开源的工程师在第一步就死了。我自己就是被这一步卡住好几年的人。

以前的开源新人最常见三种误区：

  1. 挑了一个太顶级的项目。Linux Kernel、Kubernetes、Spring Framework 这种项目，贡献门槛高、PR review 周期长、维护者忙到顾不上新人。一个新人想给 Kubernetes 提 PR，issue 选半天选不到合适的，提了 PR 等三个月都没人 review，信心直接被磨没。我当年提 Kafka 就是这个坑。
  1. 挑了一个太简单的项目。看着 good first issue 标签，挑了个改 typo 的活，提一个改文档错别字的 PR。流程跑通了，但这种 PR 在简历上没有任何说服力，面试官扫一眼就知道你只是想刷个 contribution。
  1. 自己心里没标准就劝退。GitHub 上几千万个项目，到底哪个适合自己？光这一个问题就能让人在 Trending 页面来回刷上几个月，最后什么也没做。

但 AI 时代，这三种误区都有解法了。

  1. AI 帮你筛项目。你心里没标准没关系，你只要把“什么样的项目适合我”的判断维度告诉 AI，几分钟就能跑出一份匹配你背景的候选清单。这件事以前要靠几年的开源圈子影响，现在一段提示词就能拿到。
  1. AI 帮你读懂陌生代码。挑了有技术含量的项目不再是死局，因为以前“看不懂代码就放弃”的工程师，现在可以让 AI 当导师，在不熟的技术栈、不熟的代码库上也能找到改造点。
  1. AI 帮你跨过协作门槛。写 PR 描述、写 commit message、回复 review 意见，这些以前要花大量时间打磨的东西，现在 AI 能给你一份合格初稿，你审核调整就行。

把这三件事加起来，AI 时代的开源，本质上是把“开第一个口子”这件事的成本降低了一个数量级。以前要花几年才能开始的事，现在几小时就能起步。这就是为什么 AI 时代，开源依然是，甚至比以前更是，提升竞争力的最好方式。门槛低了，但开源 commit 在简历上的分量没降。这中间的差就是工程师的红利。

接下来就是开干。AI 帮你筛项目，但你得先告诉 AI 什么样的项目才合适。下面这三道题就是这个标准。

  1. 有真实技术含量。不是 demo 项目，是真的在解决工程问题的项目。这样你提 PR 的过程中能学到东西，简历上写出来也有分量。
  1. 正在快速成长但还没到顶级。已经验证了价值方向（有几百到几千 star、有持续的 commit 活动、有几个核心维护者），但还在早期阶段（没到几万 star、没成为行业标准）。这个阶段的项目特别欢迎新人 PR，因为他们正在从“作者驱动”过渡到“社区驱动”，每一个外部贡献者对他们都是宝贵的。
  1. 跟你的技术栈或职业方向有关联。你做后端就找消息队列、数据库、缓存这类项目；做 AI 就找模型框架、Agent 框架、推理引擎；做前端就找 UI 库、构建工具。让开源经历跟你的工作互相增益，而不是再开一个赛道。

这三道题的核心思想是：跟着一个有未来的项目一起成长，你也能跟着成长。等这个项目从“快速成长”变成“行业标准”，你的早期 commit 记录会变成你最值钱的资产。

让 AI 帮我推荐项目

接下来就是按这三道题去筛项目。我把它们写成提示词，丢给 Claude Code：

我想开始给开源项目贡献代码,作为我的第一个开源 PR 的目标项目。

我的筛选标准是三道题:
1. 有真实技术含量,不是 demo 项目
2. 正在快速成长但还没到顶级(几百到几千 star、有持续 commit、
   有几个核心维护者,但还没到几万 star、没成为行业标准)
3. 跟我的技术栈或职业方向有关联

我的背景:做基础软件方向,熟悉 Java、Go、Python,Rust 在学。
对消息队列、数据库、Agent 框架这些方向感兴趣。

按这三道题给我推荐 5 个候选项目。每个项目说清楚:
- 项目定位
- star 数和最近一年的 commit 活跃度
- 维护者背景(独立团队还是大公司主导)
- 为什么适合我作为第一个 PR 目标
- 它的 good first issue 入口在哪

这个提示词的关键是把三道题显式喂给 AI，加上你自己的技术栈背景。AI 不知道你的方向，但你告诉它之后，它能在 GitHub 上跑出来一份匹配你的清单。

Claude Code 跑完给我推荐了 5 个候选。我看完那 5 个候选，挑了排在最稳那一档的项目，RobustMQ。它三道题都打中：基础软件赛道、活跃但还没到顶级、Rust 写的，跟我学习 Rust 的方向对得上。

接下来这一讲后面所有动作都在这个项目上跑。但请注意，这套流程跟具体项目无关，载体可以换成 Tokio、Tauri、Async-NATS 或者你自己 AI 推荐出来的任何项目，提示词改个项目名就能复刻。

让 AI 找最简单的 PR 入口

项目定了，接下来是选第一个 PR。

这一步的标准只有一条：走通流程比技术难度重要。第一个 PR 的目的不是证明你技术多牛，是证明你能把 fork → branch → commit → push → PR → review → merge 整条流程跑通。这条流程跑通了，后面再大的 PR 都是同一条路。

我让 Claude Code 在仓库里找最简单的 PR 入口：

我刚把这个项目的仓库 clone 下来了。我要做我的第一个开源 PR,
目标是走通完整流程,不追求技术难度。

请你扫一遍仓库的 README、CONTRIBUTING.md、docs/,看有没有专门
为新人设计的"first PR"入口。比如:
- 项目方贴心准备的简单贡献入口(签名墙、贡献者列表之类)
- good first issue 标签下的 typo 修订或文档补充
- 任何只需要改一行就能体验完整 PR 流程的入口

如果有,告诉我具体路径 + 怎么改 + 怎么提 PR。

Claude Code 跑完告诉我：这个项目在 docs 里有一个 SignYourName 入口，专门为新人贡献者设计，把自己的名字加到 SIGNYOURNAME.md 里就行。

我看完笑了。这是项目方贴心地为新人开的第一个 PR 门。表面上看就是改一行 Markdown，但它走的是完整的 fork → branch → commit → push → PR → review → merge 流程。项目方知道开源新人最怕的是开第一个口子，所以专门留了一个零技术门槛的入口给新人练手。一些活跃的开源项目都有类似的设计，你筛中的项目里有这种入口就用，没有就找一个 typo 修订或文档补充作为替代。

跑一遍 SignYourName PR

接下来就是真的跑一遍。这一遍的姿势很关键：fork 和 clone 这两步必须人工做（GitHub 账号操作 + 本地 clone），剩下所有动作都交给 Claude Code 跑。建 branch、改文件、跑 lint、写 commit、push、写 PR 描述，一段提示词丢进去全部搞定。这就是 AI 时代的 PR 工作流，不是工程师手敲一堆 git 命令。

人工的两步。

第一步，fork 仓库。在项目的 GitHub 页面右上角点 Fork，把仓库复制到自己账号下。

第二步，clone 到本地：

git clone git@github.com:<your-username>/robustmq.git
cd robustmq

剩下的全部丢给 Claude Code。在仓库目录下打开 Claude Code，丢这一段提示词：```plain我刚 fork 并 clone 了一个开源项目的仓库,要给 SIGNYOURNAME.md 加一行我的信息,作为我的第一个开源 PR。

请你帮我把整套流程跑完。每一步执行前告诉我你要做什么,执行后告诉我结果。任何报错立刻停下来问我,不要自己瞎修。

具体步骤:

  1. 建一个新 branch,命名规范跟项目已有 branch 风格对齐

(比如 feature/sign-your-name-<我的名字>)

  1. 找到 SIGNYOURNAME.md 文件,先看一眼现有列表的格式,

然后在合适的位置严格按同样格式加一行: "Robert (LoboXu) - <my-email> - 2026-05-03"

  1. 跑项目自带的代码格式检查或 lint。看 CONTRIBUTING.md /

pre-commit hook / Makefile / cargo 配置,有什么用什么。别瞎跑 cargo build,这是个 markdown 改动,只跑相关检查就行。有报错就修,跑通为止。

  1. 写一条 commit message,Conventional Commits 规范,subject

不超过 50 字符,简洁有效。然后 git add 相关文件并 commit。

  1. push 到我的 fork(remote 名是 origin)。
  1. 给我写一个 PR 描述,3-5 行,说明这是我的第一个 PR、跟着

SignYourName 入口跑通流程、表达对项目的好感、语气是普通工程师不是 LinkedIn 帖子。

  1. 如果系统装了 gh CLI,直接 gh pr create 把 PR 提了。

没装就把 PR 描述输出给我,我自己去 GitHub 点提交。``` 这段提示词的关键设计：

  1. 每一步执行前告知 + 报错立刻停，这是给 AI 装的护栏，避免它瞎修把仓库搞乱。
  1. lint 不要瞎跑 cargo build，显式告诉 AI 这是个 Markdown 改动，别在大型 Rust 项目上等几分钟编译。
  1. gh CLI 优先，fallback 人工，真实工程师有 gh 就一气呵成，没 gh 就用 AI 准备好材料、人去 GitHub 点提交。

Claude Code 跑完这一段，大概会发生这些事。

它先用 git status 确认仓库干净，然后 git checkout -b 建一个新 branch。打开 SIGNYOURNAME.md 看一眼格式，把我的信息按现有列表风格加进去。看 CONTRIBUTING.md 知道项目用 markdownlint，跑一遍发现没问题。git add + commit，commit message 是 docs: sign my name in SIGNYOURNAME.md，符合 Conventional Commits。git push 到我的 fork。最后看到我装了 gh CLI，直接 gh pr create 把 PR 提了，告诉我 PR 链接。

整个过程我做的事：只有 fork + clone + 看 AI 跑完的结果 + 在它问我的时候回答几次。手没敲过一行 git 命令，也没打开过 SIGNYOURNAME.md。

这才是 AI 时代的 PR 工作流。提示词清晰、AI 在仓库里有完整执行能力、护栏到位，工程师的角色是审核 AI 的产出和拍板，不是动手。

等 review。提交 PR 后，通常几小时到一天内会有 review。SignYourName 这种 PR 一般很快就会被合并，不要在等待期间反复刷新页面，耐心是开源的基本功。

我提交后大概一天，PR 被合并了。我的名字进了 SIGNYOURNAME.md，我的 GitHub 个人页面多了一条到这个项目的 contribution。

合并那一刻

PR 合并那一刻，你拿到的不是技术成就，是心理资产。

第一个 PR 是个里程碑。它证明了一件事：你能在不属于你的代码上做交付。这件事听起来简单，但在开源里它是分水岭。这个动作你做过一次，后面所有 PR 都是基于这个心理基础。

GitHub 个人页面上那条 contribution 不会消失，它会一直在那里。下次有面试官点进你的 GitHub，会看到你给一个真实开源项目提过 PR。这条记录从此就是你简历的一部分，甚至不需要你写在简历正文里。

更重要的是，你证明了开源没那么难，你跨过了开源新人的最大心理门槛。下一讲我们就在这个心理基础上，做一个真有难度的 PR，给一个 Rust 项目贡献一段真实业务代码，让 AI 当你的 Rust 助教。

小结

AI 时代，开源 commit 是工程师证明自己的少数几条公开可验证的路之一。它不可伪造、不可代笔、AI 写不出来，所以它在 AI 时代反而更值钱。

但开源最难的不是技术，是开第一个口子。心理门槛比技术门槛高得多。

开第一个口子的两道动作：用三道题筛项目（技术含量 + 快速成长 + 技术栈关联），用 AI 帮你找最简单的 PR 入口。两件事都不用自己刷 GitHub Trending，提示词写清楚，AI 半小时给你结果。

第一个 PR 选什么？标准只有一条：走通流程比技术难度重要。SignYourName 这种入口看着简单，但它跑的是完整 PR 流程，跑通了你后面再大的 PR 都是同一条路。

合并那一刻，你拿到的不是技术胜利，是心理资产。这一条比 PR 本身值钱得多。
