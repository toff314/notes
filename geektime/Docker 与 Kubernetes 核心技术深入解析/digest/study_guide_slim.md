# Docker 与 Kubernetes 核心技术深入解析 — 5 分钟速览

## 如果你只记住一件事
**Kubernetes 是一台"声明式期望→控制器收敛"的机器**：你只声明"我要什么"（Spec），控制器（Controller Manager/kubelet/调度器）通过 watch-队列-worker 不断把真实状态（Status）拉向期望——理解了这个模式，所有组件（调度器、控制器、kube-proxy、甚至 operator）都是同一个骨架的变体。

## 3 个核心框架
1. **Raft 选主+日志复制**：Follower 超时未收心跳→拉票→多数同意成 Leader；写操作必须经 Leader、多数确认才 commit；etcd 集群用奇数节点（3 容忍 1 坏、5 容忍 2 坏）。
2. **request≠limit 超售**：request 给调度器锁定最少需求、limit 给 cgroup 设上限，差值即超售空间——资源利用率来自业务高峰错峰共享。
3. **负载均衡=修改数据包头**：把虚拟 IP 的目标换成真实服务器地址；四种技术（NAT/新建连接/DR/隧道）只是"怎么改"的变体；切流要依赖 LB（流量必经），不能依赖 DNS（TTL 缓存滞后）。

## 5 个可操作方法
1. **list 请求务必带 resourceVersion**（信任 API Server 缓存），否则穿透到 etcd，大集群会堵死共享 gRPC 连接（L16 故障案例）。
2. **API Server 的 health check 要真实探测依赖存活**（如 etcd 实质健康），只看端口可达会在故障时"假健康"并引发大规模误驱逐（L17）。
3. **容器启动命令不要用 bash/sh 封装**——会吞掉 SIGTERM 使优雅终止失效；单容器单应用+tini，日志走 stdout（L33）。
4. **给容器设 PID/连接等资源限额**，防止"应用炸弹"（无限制 Pod 耗尽节点资源后循环摧毁整个集群）（L26）。
5. **生产环境 kube-proxy 用 IPVS 而非 iptables**——iptables 概率链在后端多时规则爆炸且全量刷新（L36）。

## 1 个反直觉观点
**Pod 里定义 1 个容器，节点上实际跑 2 个进程**——多出的 pause 容器（Sandbox）是一个永不退出的"空"底座，网络挂在它上面而非应用容器上；应用进程随便崩溃重启，网络身份不丢。这是 Pod 网络稳定性的基石（L28）。
