欢迎来到模块三的第一节课！

在前两个模块里，我们从零构建了一个功能完整的 XiaoPaw 飞书工作助手：它能理解自然语言指令，能调用飞书 API 发消息、读文档、管日历，还能通过 Skills 生态接入大量工具。从"能力"角度看，它已经相当强大了。

但如果你真的把它当日常助手用上一周，你会发现三个让人抓狂的问题：它不记得你是谁，每次对话都要重新自我介绍；说过的话要反复提，上午让它查了航班，下午问"上次那个航班几点的"——它一脸茫然；工作 SOP 要反复教，你教过它"分析阿里港股要先查实时行情、再做技术面分析、然后搜最新新闻、最后整理报告"，下次直接说"帮我分析阿里港股"，它回你"请问需要什么维度的分析？"——完全忘了。

这不是 XiaoPaw 的问题，这是所有没有记忆系统的 Agent 的通病。有意思的是，市面上已经有产品解决了这个问题。打开 Claude Code，它记得你的项目结构、你的编码偏好、上次 session 的工作进度；打开 Cursor，它知道你的代码库长什么样、你习惯用什么框架。这些产品的 Agent 为什么"有记忆"？不是因为模型本身能记住，而是因为它们背后有一套精心设计的记忆工程。这就是本模块要解决的核心问题：让 XiaoPaw 从一个"每次都失忆的工具人"，变成一个"懂你、记得你、越用越顺手"的长记忆助手。

今天这节课，我们先不写代码，而是建立一个关键的认知框架——理解记忆到底是什么、它是怎么演进的、以及我们该如何治理它。

一、 认知原点：记忆的本质到底是什么？

先把一个可能的认知误区拿出来说清楚。

当你在 ChatGPT 里连续对话，感觉它"记住"了你之前说的话——很多人以为这是模型的能力。其实不是。大模型没有记忆。每一次 API 调用都是独立的，模型不知道你上一句说了什么。

那为什么它"记得"？因为应用层把你之前的对话历史，悄悄塞进了这次请求的 message list 里。

记忆的本质，就是一套构建 message list 的机制。 模型的"记忆"，其实是因为你默默地告诉了它。

# 这就是"记忆"的全部真相
messages = [
    {"role": "system",    "content": "你是XiaoPaw，一个飞书工作助手..."},
    {"role": "system",    "content": "用户偏好：周报格式先汇总再列计划..."},  # ← 这就是"记忆"
    {"role": "user",      "content": "帮我发周报"},
    {"role": "assistant", "content": "好的，我来按你喜欢的格式..."},
]

你往 messages 里塞了什么，模型就"知道"什么。你没塞的，它就不知道。没有魔法，只有信息流设计。如果把大模型类比成一台电脑：模型本身 = CPU，只负责计算，不存储；上下文窗口 = 内存（RAM），容量有限，断电就没了；外部存储（文件、数据库）= 硬盘，持久化但需要主动读取。

记忆系统要做的事情，就是设计一套机制：什么时候从"硬盘"加载到"内存"，什么时候从"内存"写回"硬盘"，"内存"快满了怎么腾空间。这个类比贯穿整个模块三——后面每一课都在解决这个"内存管理"问题的不同侧面。

二、 为什么需要它：三代演进背后的驱动力

既然记忆的本质是"构建 message list"，那这件事是怎么一步步演进的？

这个演进不是凭空发生的，它由两条线同时驱动：模型能力的变化和产品形态的变化。

Prompt Engineering：人写全部

最早的 AI 产品就是聊天机器人。用户问一句，模型答一句。没有工具调用，没有多步推理，整个上下文就是用户写的那句话。

那个时代的模型（GPT-3 时代）对词汇表述极度敏感——你说"请总结这段文字"和"请概括这段文字"，可能得到完全不同质量的回答。所以那个时代的核心技能叫 Prompt Engineering——本质是在研究"用什么词能触发模型的最佳表现"。上下文管理？不需要管理。人写的提问就是全部上下文。

Context Engineering：工程逻辑构建

当 AI 产品从"聊天"进化到"做事"——用 Workflow 编排多步流程，用单 Agent 调用工具完成任务——message list 里不再只有用户的话，还有工具返回的数据、中间步骤的结果、其他 Agent 的输出。

模型的语义理解能力大幅提升，你不用再抠字眼了。但新的问题来了——工具返回的数据质量参差不齐，垃圾数据进了上下文，模型照样会被带偏。工程师要决定：哪些工具返回值放进 message list、放多少、什么时候截断、什么时候压缩。

这就是 Context Engineering 的核心——在有限的 token 预算内，组装出最高质量的上下文。这个概念由 Andrej Karpathy（前 Tesla AI 负责人）在 2025 年中正式提出，Shopify CEO Tobi Lutke 进一步推广。

Harness Engineering：设计环境让模型探索

当任务变成"帮我重构这个代码库""帮我做一份竞品分析报告"——没有预定义的步骤，Agent 需要自己决定下一步做什么、读什么文件、调什么工具。你没法提前编排 message list，因为你不知道 Agent 会走哪条路。

这就是 Harness Engineering。Harness 这个词是 OpenAI 在 2026 年 2 月正式提出的，字面意思是"马具"——套在马身上的缰绳、鞍具、挽具。

如果模型是一匹马，Prompt 时代你是骑手，手把手拉缰绳告诉它每一步怎么走。Context 时代你是教练，给它规划好赛道和路线。Harness 时代你是牧场主，你建好围栏、水源、草料站，马自己决定去哪吃草、去哪喝水——但它永远跑不出你设计的牧场。

有一个常见误区需要纠正：Harness 时代不是"完全放手让模型自己搞"。现实中即使是最先进的 Claude Code，也依赖 CLAUDE.md 预加载项目结构、rules/ 预加载约束、MEMORY.md 前200行自动注入记忆索引。正确的理解是：预加载关键索引 + 模型按需探索的混合模式。

三、 治理框架：加法与减法

理解了三代演进之后，我们回到一个核心问题：不管哪个时代，上下文治理的本质就是两件事——加法和减法。

加法：让模型知道它该知道的

加法解决的是"模型不知道它该知道的事"。回到开篇的三个痛点：不记得你是谁，需要把用户画像加进上下文；说过的话要反复提，需要把历史对话摘要加进上下文；SOP 要反复教，需要把工作规范加进上下文。

加法的四种主要手段：

  1. Bootstrap 预加载：启动时固定加载的信息（人设、规则、记忆索引）。类比：员工入职时发的员工手册，每天上班第一件事就是翻开来看。
  1. 工具返回注入：Agent 调用工具后，结果自动进入上下文。类比：员工查完资料后脑子里多了一条信息。
  1. 记忆检索注入：从持久化存储中检索相关记忆，注入当前上下文。类比：员工翻看自己的工作笔记，找到相关记录。
  1. Skill 按需加载：渐进式披露，模型判断需要时才加载完整内容。类比：员工需要时才去翻操作手册的具体章节，而不是把整本手册背下来。

减法：让上下文没有不该有的

加法的冲动是无限的——恨不得把所有信息都塞给模型。但减法告诉你：不能这么干，而且不应该这么干。

为什么"不能"？因为上下文窗口有物理上限。

为什么"不应该"？两个原因。

原因一：Context Rot（上下文腐化）。 上下文越大，模型的注意力越分散，对每条信息的关注度越低。这不是"可能会"，而是 Transformer 架构的物理规律——后面 Under the Hood 部分会详细讲。研究数据显示，随着上下文增长，模型性能会显著下降。

原因二：成本。 大模型按 token 计费，Transformer 的计算复杂度是 n 的平方。上下文翻倍，成本翻四倍。即使未来模型再强、窗口再大，这个经济约束不会消失。上下文工程不只是能力问题，更是经济问题。

减法的三种主要手段：

  1. 压缩 / 截断：把旧的对话历史压缩成摘要，或者直接截断超出窗口的部分。
  1. 选择性遗忘：不是所有信息都值得留在上下文里，要主动丢弃低价值信息。
  1. Sub-agent 隔离：把任务委派给子 Agent，子 Agent 用干净的上下文独立工作，结果汇总回主 Agent。主 Agent 的上下文始终保持精简。

四、 深入框架：Context Rot 的底层运行机制

前面说"上下文越大，模型表现越差"，这不是经验之谈，而是 Transformer 架构的物理规律。把这个黑盒撕开来看。

注意力是一个有限预算

Transformer 模型处理信息的核心机制是"注意力"（Attention）。模型在生成每一个 token 时，会"看一眼"上下文里的所有其他 token，决定每个 token 对当前生成有多重要。

关键在于：注意力是一个有限预算。 上下文里有 1000 个 token，每个 token 分到的注意力是 1/1000；有 100000 个 token，每个 token 分到的就是 1/100000。上下文越长，每条信息被"认真看"的程度越低。

这就是 Context Rot 的物理根因：不是模型"忘了"，而是注意力被稀释了。

超过 40%，能力开始下降

研究发现，当上下文使用量超过约 40% 时，模型能力会出现显著下降。这不是线性退化，而是一个明显的拐点——超过这个警戒线，性能持续走低。

这个数字的工程含义很直接：不要等上下文快满了才想起来治理，要在 40% 之前就主动管理。

U 型注意力分布

研究还发现（Liu et al., TACL 2024），模型对上下文不同位置的关注度呈 U 型分布：开头和结尾的信息被关注得最多，中间的信息最容易被"忽略"。

这解释了几个你可能注意到的现象：System Prompt 放在最前面，是在利用开头的注意力高点；最近几轮对话最重要，是在利用结尾的注意力高点；中间的历史对话最容易丢失信息，因为它处于注意力低谷。

Claude Code 的 System Reminder 机制就是基于这个原理：每次工具调用后，自动在消息末尾注入关键提醒，把重要信息持续推到 U 型曲线的"结尾高点"。

理解了这个底层逻辑，你完全可以做出更精准的设计决策：关键信息放两头，中间地带要精简，不要迷信大窗口——即使模型支持 100 万 token，塞满 100 万 token 的效果远不如精选 1 万 token。

本课总结

  • 我们揭开了记忆的本质：大模型没有记忆，所谓"记住"，是因为应用层把信息塞进了 message list——你往里塞了什么，模型就知道什么，没有魔法，只有信息流设计。
  • 我们梳理了三代演进：从 Prompt Engineering（人写全部）到 Context Engineering（工程逻辑构建 message list），再到 Harness Engineering（预加载索引 + 模型按需探索），控制权从"写内容"转向"造环境"。
  • 我们建立了治理框架：加法让模型知道该知道的，减法让上下文没有不该有的——两者缺一不可，只做加法不做减法，上下文必然腐化。
  • 我们理解了 Context Rot 的物理根因：注意力是有限预算，上下文超过 40% 后能力显著下降，U 型分布决定了关键信息要放两头、中间要精简。
  • 我们提炼了三大核心问题：记什么、怎么存、怎么取——这是后续四课的统一框架，每课都会从这三个角度展开。
