欢迎来到第 26 节课！

上节课，我们设计了 Manager、PM、Dev、QA 四个数字员工——每个人有自己的职责宪章（Role Charter）、灵魂配置（Soul）、独立记忆（Memory）和专属技能（Skills）。乍一看，这个团队已经"组建完成"了。

但组建完成和真正能协作，是两回事。

想象这样一个场景：Manager 已经把需求拆好了，想让 PM 去写产品文档——PM 怎么知道这个任务？任务的详细说明在哪里？PM 写完文档以后，放在哪里？Manager 怎么知道"PM 已经完成了"？做完验收，结论存到哪里让后续的 Dev 看到？

这一系列问题，都不是角色设计本身能回答的——它们属于另一个独立的工程问题：多角色之间的协作协议。

本课就来解决这个问题。我们会引入数字员工团队的两种核心机制——共享工作区和邮箱——复用人类项目管理几十年来验证有效的两套思路，用工程方式实现一个真实可运行的多角色协作流水线。

一、认知原点：协作协议的本质到底是什么？

协作协议的本质，就是解决两个独立问题：谁能看到什么（状态共享），以及谁来告诉谁做什么（任务触发）。

这不是 AI 特有的挑战。在人类的项目团队里，你早就见过这两个问题的答案——

状态共享靠公共区域。想想你在公司做一个大项目的时候——不管是飞书也好、Confluence 也好，你们都有一个"项目空间"，需求文档、设计稿、代码、测试报告，所有共享的东西都存在那个地方。任何人需要背景信息时，去公共区域找，不需要问人，不需要等人回复。

任务触发靠消息/邮件。假设你们都是远程办公——Manager 通过飞书或邮件告诉你"你今天接一个活"，或者一个群发通知所有人"接下来你们都干啥"。任务完成后，执行者回复通知，经理进行验收。开会、站会之类的，本质上也是这两种机制的变体。

如果你用过 Confluence + Jira，你已经见过这两种机制的工具化版本——Confluence 是公共区域（状态共享），Jira 是邮件任务系统（任务触发）。它们不是凭空发明的，是几十年软件工程实践提炼出的最小协作基础设施。

数字员工团队需要的，是完全相同的两种机制——只不过用文件和 JSON 来实现：共享工作区负责状态共享，邮箱负责任务触发。两种机制解决不同的问题，不要混用——工作区不能发通知，邮件不能存文档。

把这两种机制分清楚，是本课最重要的认知原点。很多人一开始的直觉是"让 Agent 互相调用不就行了？"——这忽略了一个关键差异：工作区和邮箱解决的是不同时间维度的问题。工作区存的是持久化的状态，任何时候都可以读；邮箱传递的是时序性的事件，发出去的消息有明确的发出时间和接收者。两者混用，会造成架构混乱。

二、为什么需要它：没有协作协议，团队会怎样崩溃？

我们来还原一下，如果没有共享工作区和邮箱机制，一个"组建完成"的多角色团队会遇到什么。

第一个崩溃时刻：信息传递靠上下文注入，上下文爆炸。

最直接的方案是：Manager 在调用 PM 时，把所有背景信息直接写进 prompt——需求文档全文、项目背景、验收标准，全部塞进去。PM 的上下文一次性加载完所有东西，然后开始工作。

这个方案在小任务时能跑，规模一大立刻崩。需求文档可能有几千字，设计文档又几千字，代码历史又几千字——几个角色串联下来，每次调用的 token 消耗以指数级上涨。更糟糕的是：PM 看到的需求是 Manager 复制进去的一份快照，Manager 若在后续更新了需求，PM 手里的版本还是旧的，两边的状态出现了分叉。

第二个崩溃时刻：任务触发靠硬编码顺序，动态性为零。

另一个方案是：直接在编排代码里写死顺序——先跑 Manager，再跑 PM，再跑 Dev。这是传统框架默认的顺序执行模式。

这个方案的问题在于：真实项目不是线性的。Manager 可能需要先等 PM 的文档出来，再决定分配给哪个 Dev；某个任务失败了，可能需要重新触发；两个 Dev 可以并行工作。一旦流程有条件分支、重试、并发，硬编码顺序就彻底失控——你会发现自己在用"框架层的 if-else"来模拟"业务层的任务调度"，这是把两层关注点混在一起的典型设计失误。

第三个崩溃时刻：没有持久化协议，结果无从共享。

Manager 验收完 PM 的产品文档，觉得不错——但这个结论存在哪里？它现在在 Manager 的上下文里，下一次调用时会消失。Dev 需要这个结论作为开发输入，但 Manager 的上下文对 Dev 不可见。

没有持久化协议，每个角色的输出都是"孤岛"——只存在于当次调用的上下文中，无法跨角色、跨 session 传递。多角色协作变成了"每次调用互相不认识"的松散烟花，而不是有记忆的持续协作。

三、两种机制的设计与实现

解法很清晰：用共享工作区解决"状态在哪里、我能看什么"，用邮箱解决"谁让我做什么、我做完告诉谁"。下面逐一展开。

3.1 共享工作区：结构化、有权限、Manager 定规则

共享工作区不是随便堆文件的地方——它是一个精心设计的状态系统，有结构、有权限边界、有 Manager 制定的访问规范。

本课代码的工作区结构如下：

workspace/
├── shared/                     # 所有角色可访问的共享区
│   ├── needs/                  # 需求文档（Manager 写入）
│   │   └── requirements.md
│   ├── design/                 # 产品设计（PM 写入）
│   │   └── product_spec.md
│   └── mailboxes/              # 邮箱目录（所有角色通过 mailbox Skill 读写）
│       ├── manager.json
│       └── pm.json
├── manager/                    # Manager 个人工作区（私有）
│   ├── agent.md                # 工作规范
│   ├── soul.md                 # 灵魂配置
│   └── skills/                 # 专属 Skills
└── pm/                         # PM 个人工作区（私有）
    ├── agent.md
    ├── soul.md
    └── skills/

权限边界是工作区设计的核心。PM 可以读 needs/，但只能写 design/；Manager 可以读写整个共享区，但不能替 PM 写产品文档。这个边界不是靠 AI 自律来保证的——权限控制的目的不是防止 AI 作弊，而是缩小注意力范围。PM 的 agent.md 告诉它"需求在 needs/，文档写到 design/"，它的注意力就精准集中在这两个目录；如果没有这个约束，它可能会去翻 manager/ 的历史记录，引入无关的上下文噪声。

访问规范如何传递？ Manager 把当前项目的工作区规范写成 WORKSPACE_RULES.md，打包成一个 reference skill（第 16 课已经学过这个模式）。每个数字员工在访问共享区之前，先通过 skill_loader 加载 workspace-rules，注入当前项目的访问规范。

这个设计有一个关键好处：规范不是硬编码的，而是 Manager 根据每个项目动态制定的。想想看：如果当前项目是研发类项目，工作区就是 needs/、design/、code/、qa/ 这个结构；但如果同样的数字员工团队接到的任务是做竞品调研呢？那 Manager 定出来的工作区就不是这样了——可能只需要 PM 和 Dev 参与，目录变成 research/、analysis/、report/。再比如做股票交易，那就是 market_data/、strategy/、trades/——完全不同的结构。

也就是说，同一个团队，面对不同项目，workspace 长什么样完全取决于 Manager 当时拿到的需求。Manager 有 init_project Skill 来告诉它怎么建工作区，但具体建成什么样，是 Manager 基于需求动态决定的。拿到这个 workspace 和规则之后，其他角色才根据 WORKSPACE_RULES.md 来执行具体的文件操作。这是"Manager 定规则、成员按规则执行"的分层设计。

对应人类项目经理在项目开始时创建 Confluence 空间、设定文件夹结构、初始化各成员工作目录的动作，本课代码在 tools/workspace_ops.py 中提供了 create_workspace 函数：

# tools/workspace_ops.py

3.2 邮箱：有结构的消息，不是自由文本

邮箱是数字员工之间任务触发的基础设施。每个数字员工有自己的邮箱文件，管理在 shared/mailboxes/ 目录下。Claude Code 的团队模式（Team Mode）也是用文件邮箱系统来实现成员间协作的——我们不是在发明新东西，而是沿用行业验证过的设计思路。

消息的数据结构是这样的：

{
  "id": "msg-a1b2c3",
  "from": "manager",
  "to": "pm",
  "type": "task_assign",
  "subject": "产品文档设计",
  "content": "请根据 /mnt/shared/needs/requirements.md 设计产品规格文档，完成后写入 /mnt/shared/design/product_spec.md",
  "timestamp": "2026-04-10T10:00:00+08:00",
  "status": "unread",
  "processing_since": null
}

每个字段都有明确用途：

  • from / to：发件人和收件人，支持单发（指定一个角色）和群发（数组）；
  • type：消息类型——task_assign（任务分配）、task_done（任务完成）、broadcast（广播通知）。类型字段至关重要：接收方不需要用 LLM 推理"这条消息要我做什么"，直接通过 type 知道处理逻辑，降低误判率；
  • content：任务说明。注意：content 里只写路径引用，不复制文档全文——Manager 给 PM 发邮件的时候，不会把需求文档的全部内容塞进邮件正文，而是说"需求在 /mnt/shared/needs/requirements.md，你自己去读"。PM 完成后也一样，"产品文档已写入 /mnt/shared/design/product_spec.md"。这样，邮件始终保持轻量，真正的文档在共享工作区——这就是"邮箱只传事件，工作区存状态"的核心分工；
  • status：消息处理状态，三个值——unread（新写入）、in_progress（已取走正在处理）、done（处理完成）。为什么不用简单的 read: bool？3.4 节详细解释；
  • processing_since：进入 in_progress 时记录的时间戳，用于崩溃检测（见 3.4 节）。

你可能会问：为什么不直接让 Manager 发自然语言消息，让 PM 的 LLM 自己理解？

原因在于工程可靠性。自由文本消息在简单场景下没问题，但它把解析责任推给了接收方的 LLM——每次接收都要推理"这是任务分配还是仅通知"，增加了误判概率。结构化消息让路由逻辑变成确定性代码，而不是概率性推理。

3.3 文件锁：邮箱并发写入的工程保护

邮箱的核心危险场景是并发写入。假设 Manager 和 Dev 同时向 PM 的邮箱发消息——两个进程同时读取 pm.json（都读到旧内容），各自追加一条消息，各自写回文件——后一次写入会覆盖前一次，消息丢失。这就是 last-write-wins 问题。

解法是 filelock——在读取和写入之间加文件锁，把"读 + 追加 + 写"变成原子操作：

# tools/mailbox_ops.py 核心逻辑
from filelock import FileLock

def send_mail(mailbox_dir, to, from_, type_, subject, content):
    inbox  = mailbox_dir / f"{to}.json"
    lock   = inbox.with_suffix(".json.lock")

    with FileLock(str(lock)):               # 💡 核心点：锁住整个"读-追加-写"流程
        messages = json.loads(inbox.read_text())
        messages.append({
            "id":               f"msg-{uuid.uuid4().hex[:8]}",
            "from":             from_,
            "to":               to,
            "type":             type_,
            "subject":          subject,
            "content":          content,
            "timestamp":        datetime.now(timezone.utc).isoformat(),
            "status":           "unread",   # ← 三态起点
            "processing_since": None,
        })
        inbox.write_text(json.dumps(messages, ensure_ascii=False, indent=2))

  1. 标记为in_progress而不是done——Agent 取走消息后可能崩溃，直接标 done 会导致消息永久丢失（见 3.4 节）；
  1. 返回快照而不是原始引用——dict(m) 创建副本，避免调用方意外修改 JSON 结构；
  1. 锁在读取之前就要加上——不是读完再加锁，否则两个进程可能同时读到 unread 的旧状态。

3.4 已读状态的状态机：为什么不是简单的 true/false

这是本课最容易被跳过、但在生产中最容易踩坑的工程细节。

两态设计的致命漏洞。 最直觉的做法是 read: bool——Agent 取走消息时标记 read: true，轮询器跳过已读消息。这个设计有一个隐患：取走（read_inbox）和处理完成之间，存在一个时间窗口。Agent 取走消息后，进入 LLM 推理阶段——如果此时进程崩溃（内存溢出、网络超时、容器被杀），消息已经是 read: true，下次轮询时被跳过，任务永久消失，没有任何报错。

想想看：Manager 已经给 PM 发了一个任务，PM 收到邮件后挂了。其他数字员工不知道要干啥，Manager 一直在等 PM 的回复。如果这个消息直接标了 done，PM 再也找不回来了——整个任务链就直接夯死。这就跟我们人一样——你发了一条消息出去，隔了半个小时对方还是未读，"已图不回"，那你就知道触达可能有问题了，得再想办法。

三态状态机解决了这个问题。 消息有三个状态：

unread  ──(read_inbox)──►  in_progress  ──(mark_done)──►  done
                               │
                               └──(超时/崩溃)──► unread（reset_stale 重置）
  • unread：消息写入，等待被取走；
  • in_progress：已被取走，正在处理中。轮询器跳过此状态（不重复取走）；
  • done：处理完成，由编排层在确认 Agent 成功完成后调用 mark_done 确认。

关键分工：read_inbox 负责原子地把消息从 unread 改为 in_progress（同时记录 processing_since 时间戳）；mark_done 负责在处理成功后把消息改为 done——这是两个独立的步骤。

崩溃恢复：reset_stale和"补单"机制。 每个数字员工可以有一个后台定时任务（参考第 17 课的 CronService），比如每隔十分钟唤醒一次，调用 read_inbox 取走 unread 消息并处理。如果发现有一条十分钟前就已经是 in_progress 的邮件、但一直没有完成——说明上次处理到一半崩了。这时 reset_stale 会把超时的 in_progress 消息重置回 unread，下次轮询就能重新处理。

这个概念在金融交易系统里叫"补单"——交易到一半系统崩了，恢复后扫描所有"已发起但未完成"的订单，进行补处理。我们用三态状态机在邮箱层面实现了完全相同的语义。本质上，这就是 AWS SQS 的 Visibility Timeout 模式——消息被取走后进入"不可见"状态，处理完 delete（mark_done），超时不 delete 则重新可见（reset_stale）。

# 后台 Watchdog（参考第17课 CronService）
def watchdog():
    reset_stale(MAILBOXES_DIR, role="pm", timeout_seconds=900)

只有这样一套三态状态机，才能保证所有通知都是可靠的——不会在中间丢掉，同时同步通知又非常快。

3.5 通知机制：同步触发 + 后台轮询互补

消息的状态机解决了"不重复、不丢失"问题；但 PM 需要知道消息到了——这是触发机制的问题。

同步通知（主动唤醒）：Manager 发完邮件后，编排层立刻启动 PM 的 session。比如本课代码中，Manager 跑完 main.py 后，你手动执行 python start_pm.py 来启动 PM——这就是在模拟同步通知。优点是及时，延迟极低；缺点是如果 PM 的 session 启动失败（崩溃、超时），消息停留在 unread。

后台轮询（定时检查）：每个数字员工有一个后台定时任务（参考第 17 课的 CronService），每隔几分钟唤醒一次，调用 read_inbox 取走 unread 消息并处理。这是兜底机制——即使同步通知失败，下次轮询时会补处理。

两者的关系：互补、互斥。同一条消息不会被处理两次——in_progress 的消息轮询时跳过（三态状态机的互斥保证）。同步通知负责"快"，后台轮询负责"兜底"，两者合力保证任务不丢失、不重复处理。平时靠同步通知实时响应，定时任务负责兜底——消息快又不丢。

四、代码实战：Manager → PM → Manager 三步任务链

🧠 回忆一下：上节课我们用 DigitalWorkerCrew 框架让每个数字员工在自己的沙盒里独立运行，通过 agent.md 定义工作规范、通过 skill_loader 加载 Skills——还记得吗？本课的代码就是在那个框架上新增邮箱和工作区的协作能力。

本课代码演示 Manager + PM 两角色的完整三步协作流程：

步骤 1（Manager）：初始化工作区 → 写需求 → 发 task_assign 邮件给 PM
步骤 2（PM）    ：收邮件(→in_progress) → 读需求文档 → 写产品文档 → 发 task_done 邮件给 Manager → 标记消息 done
步骤 3（Manager）：收邮件(→in_progress) → 读产品文档 → 写验收结论 → 标记消息 done

核心架构 ``plain m4l26/├── main.py # Manager 入口（分配模式 / 验收模式自动切换）├── start_pm.py # PM 入口（检查邮箱 + 执行任务）├── tools/│ ├── mailbox_ops.py # send_mail / read_inbox / mark_done / reset_stale│ └── workspace_ops.py # create_workspace（初始化工作区）├── sandbox-docker-compose.yaml # Manager 沙盒（8025）+ PM 沙盒（8026）└── workspace/├── shared/ # 共享工作区│ ├── needs/ # 需求文档（Manager 写入）│ ├── design/ # 设计文档（PM 写入）│ └── mailboxes/ # 各角色邮箱├── manager/ # Manager 个人工作区（agent.md + soul + skills）└── pm/ # PM 个人工作区（agent.md + soul + skills）``本课的设计哲学是：Manager 和 PM 各自独立启动，Agent 基于 workspace-local Skills 自主决策。这跟过去框架里的主 Agent 起 sub-agent、sub-agent 干完活就销毁的模式完全不同——这里的每个数字员工都是独立运行的，它自己读邮箱、自己加载 Skill、自己决定干什么。

课程为了方便理解和 debug，本课采用手动串联的方式——先跑 Manager、再手动启动 PM、再跑一次 Manager 验收。到第 29 课，我们会让 Manager 和 PM 成为真正的常驻数字员工，由系统自动触发。

运行方式：

# 步骤 1：Manager 启动（初始化工作区 + 分配任务给 PM）
python main.py

# 步骤 2：PM 启动（检查邮箱 + 完成任务）
python start_pm.py

# 步骤 3：Manager 再次启动（自动检测邮箱 → 验收）
python main.py

关键代码：Manager 的自动模式切换 main.py 的核心设计是根据邮箱状态自动决定本轮任务——如果 Manager 邮箱里有 PM 发来的 task_done 消息，就进入验收模式；否则按新项目流程分配任务：

# main.py
def _has_pending_task_done() -> bool:
    """检查 Manager 邮箱是否有待处理的 task_done 消息。"""
    manager_inbox = MAILBOX_DIR / "manager.json"
    messages = json.loads(manager_inbox.read_text())
    return any(
        m.get("type") == "task_done" and m.get("status") in ("unread", "in_progress")
        for m in messages
    )

def _build_user_request() -> str:
    if _has_pending_task_done():
        return "请检查你的邮箱，验收 PM 发来的产品文档..."    # 💡 验收模式
    else:
        return f"你收到了新项目需求，请完成任务分配..."        # 💡 分配模式

这个设计的价值在于：Manager 不需要外部编排器告诉它"现在该验收了"——它自己检查邮箱状态就知道。两次调用 python main.py，同一段代码自动切换行为，完全由文件状态驱动。

Manager 分配任务时做了什么？

Manager 启动后，按照 agent.md 的工作场景一执行：

  1. 加载 init_project Skill → 在沙盒中执行 init_workspace.py，创建共享工作区结构
  1. 将需求写入 /mnt/shared/needs/requirements.md
  1. 加载 mailbox Skill → 调用 mailbox_cli.py send 给 PM 发 task_assign 邮件
  1. 读取 pm.json 确认消息已写入

注意邮件内容的写法——Manager 不会把需求文档全文塞进邮件正文。它只是说"需求在 /mnt/shared/needs/requirements.md，你自己去读，产品文档写到 /mnt/shared/design/product_spec.md"。这样邮件始终简短，真正的数据交换通过共享工作区完成。

PM 执行任务时做了什么？

start_pm.py 启动 PM 后，PM 按照自己的 agent.md 工作规范执行：

  1. 加载 mailbox Skill → 检查邮箱，发现 task_assign 任务
  1. 根据邮件指示，到共享区读取需求文档
  1. 加载 product_design Skill → 撰写产品规格文档
  1. 将文档写入 /mnt/shared/design/product_spec.md
  1. 加载 mailbox Skill → 给 Manager 发 task_done 邮件，标记原消息 done

两个设计决策值得注意。

第一，main.py 通过读文件判断状态（而非等待 LLM 输出）来决定工作模式。这是工程上的显式边界——不依靠 LLM 自我报告"上次我做过什么"，而是通过可观测的状态（邮箱文件是否有 task_done 消息）来确认当前阶段。

第二，mark_done 由 Agent 自己在确认完成后调用（通过 mailbox_cli.py done 命令），而不是由外部编排器调用。这跟 v2 的设计不同——在独立 Agent 模式下，Agent 自己知道自己的任务是否完成了，完成后自己标记 done 是合理的。编排器层面只负责启动 Agent，不介入 Agent 的内部工作流。

五、深入框架：邮箱系统的底层运行机制

我们来把邮箱这个机制的外衣撕开，看看一条消息从 Manager 发出到 PM 处理，中间经历了什么。

第一步：Manager 的 Agent 在沙盒中调用mailbox_cli.py send，参数包含收件人、类型、主题、正文。CLI 脚本调用 mailbox_ops.py 的 send_mail 函数——这是纯 Python 函数，不经过 LLM。邮箱操作本身不涉及代码执行风险，直接 Python 调用更快更可靠。

第二步：send_mail函数获取文件锁，锁定 pm.json.lock 文件（filelock 库实现跨进程锁）。锁在文件读取之前就加上——如果另一个进程已经持有锁，当前进程阻塞等待，直到锁被释放。

第三步：读取现有邮件列表，追加新消息，写回文件，释放锁。 这三步在同一个 with FileLock(...) 块内，无论中间发生什么（进程崩溃、网络中断），文件要么没有写入旧状态，要么完整写入新状态，不会产生半写状态。

第四步：Manager 完成本轮任务，main.py 退出。此时 PM 的邮箱里已经有了一条 unread 的 task_assign 消息。

第五步：手动执行python start_pm.py（模拟同步通知或定时唤醒），PM 的 Agent 启动后，通过 mailbox Skill 调用 mailbox_cli.py read，内部走 read_inbox 函数——原子标记为 in_progress。这里有三个精妙细节：一是标记 in_progress 而不是 done——Agent 可能在处理途中崩溃；二是同时记录 processing_since 时间戳——Watchdog 后续用它判断是否超时；三是返回快照副本（dict(m) 而不是原始引用）——调用方对返回值的修改不影响文件里的数据。

第六步：PM 完成任务后，调用mailbox_cli.py done标记消息完成。如果 PM 在这一步之前崩溃，消息停留在 in_progress；后台 Watchdog 在超时后调用 reset_stale，将消息恢复为 unread，下次轮询时重新处理——这就是前面讲的"补单"机制。

整个链路下来，消息从 Manager 到 PM 的传递是完全异步的——Manager 写完文件就可以退出或做下一件事，不需要等 PM 处理完。PM 处理完后，通过同样的机制回邮给 Manager。这是一个典型的"生产者-消费者"模式，文件充当了消息队列的角色。

理解了这个底层逻辑，哪怕不用 filelock 库，你完全有能力手搓一套原子写入机制——用 tmp 文件 + os.rename 原子重命名，是不需要锁的另一种实现方式（Maildir 协议就是这个思路）。三态状态机也可以用 Redis 的 SETNX 或 PostgreSQL 的 SELECT FOR UPDATE 实现——机制相同，存储不同。后续如果你的场景更复杂，邮件系统甚至可以做成一个独立的 MCP 服务，Agent 通过 MCP 协议来收发邮件。

六、避坑指南：最佳实践与反模式

🚫 严重破坏稳定性的"反模式"

反模式一：多 Agent 并发写同一文件，没有文件锁

现象：两个 Agent 同时向同一个角色（比如 PM）发邮件。两个进程同时读取 pm.json（都看到旧版本），各自追加一条消息，各自写回文件——后一次写入覆盖前一次，一条消息永久丢失，且没有任何报错。

致命后果：消息丢失是静默的——LLM 不会报错，Agent 不知道消息没到，整个任务链在某一步卡死，日志里看不到原因。在并发场景（多个 Agent 同时激活）下，这是多 Agent 文件系统交互中最常见的生产故障来源。

反模式二：两个 Agent 都认为自己能写同一目录

现象：Manager 和 PM 都认为自己可以更新 needs/requirements.md（需求文档）。Manager 在验收时顺手把"发现的问题"追加进需求文档；PM 在写产品文档时把需求重述一遍也写进去——两个角色同时维护同一份"权威文档"，版本很快分裂。

致命后果：MAST 分类法研究表明，inter-agent 误对齐占所有 Agent 失败模式的 37%，而其中最常见的根因是资源所有权不唯一——两个 Agent 都觉得"这是我负责的"。修复方案不是加锁，而是从设计层消除歧义：每个文件/目录只有一个 Owner。

💡 稳健落地的"最佳实践"

最佳实践一：写文件尽量用 rename 方式，邮件内容只传路径引用

落地心法：JSON 文件写入有个过程——如果写到一半进程被杀，文件就处于半写状态（半截 JSON），后续所有读取都会 parse 失败。更安全的方式是先写到临时文件（pm.json.tmp），再用 os.rename 原子重命名覆盖原文件——rename 在 Linux 上是原子操作，要么成功要么不动。同时，邮件内容只写路径引用、不把文档全文塞进去——共享区里写好东西以后，真正触达的时候只需要一个小邮件。邮箱始终轻量，大文件在工作区。

最佳实践二：每个文件/目录只有一个 Owner，Owner 才能写

落地心法：在 WORKSPACE_RULES.md 里为每个目录明确声明 Owner（如 design/ → PM），非 Owner 角色只给读权限，不给写权限。Agent 的 agent.md 工作规范里强制这个约束——PM 的工作场景只让它写 design/，写其他目录直接在规范层面禁止。Owner 制度的价值在于：当文档格式出了问题，你立刻知道是谁负责——Owner 是唯一可问责的角色，职责清晰则修复快。

最佳实践三：消息必须是三态状态机（unread → in_progress → done）

落地心法：不要用简单的 read: true/false，必须用三态。unread → in_progress → done，只有这样才能保证整个消息的可靠——不会因为某个 Agent 崩溃而夯住。做过金融相关业务的对这种模式都比较熟悉——补单、重试、幂等，都是同一套思路。in_progress 状态加上 processing_since 时间戳，是崩溃恢复的关键线索。

最佳实践四：同步通知 + 后台轮询互补，而不是二选一

落地心法：同步通知用于主路径（Manager 发邮件后立刻唤醒 PM），轮询用于兜底（每隔几分钟 + 随机 jitter，处理同步通知失败的漏网消息）。两者通过 status 字段自然互斥——同步通知处理过的消息已经是 in_progress 或 done，轮询时直接跳过，没有额外协调成本。这个组合在两个角色运行在同一台机器上的场景是性价比最高的选择：实现轻量，行为可靠。

课程总结

  • 我们识别了"角色完成 ≠ 协作可靠"的根本原因——状态共享（谁能看到什么）和任务触发（谁来告诉谁做什么）是独立于角色定义的工程问题，需要独立设计，不能混用。
  • 我们引入了数字员工团队的两种协作机制：共享工作区（结构化目录 + 权限边界 + Manager 动态制定 workspace-rules）处理持久化状态，邮箱（结构化 JSON + type + status 字段）传递时序性事件。共享工作区里的结构不是硬编码的——同一个团队做研发项目和做竞品调研时，workspace 的结构完全不同，都由 Manager 根据需求动态定义。
  • 我们实现了文件锁（FileLock）保护并发写入，用"读-追加-写"原子操作消除 last-write-wins 问题；用三态状态机（unread → in_progress → done）实现消息的可靠投递，借鉴金融系统"补单"机制保证崩溃可恢复。
  • 我们演示了 Manager → PM → Manager 的三步任务链：Manager 和 PM 各自独立启动，基于 workspace-local Skills 自主决策，通过可观测的文件状态（而非 LLM 自我报告）确认进度，同步通知保证及时响应，后台轮询保证不丢消息。
