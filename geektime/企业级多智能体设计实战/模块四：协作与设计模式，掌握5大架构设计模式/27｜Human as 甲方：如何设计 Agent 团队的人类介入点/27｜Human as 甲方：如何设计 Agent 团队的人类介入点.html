欢迎来到第 27 节课！

上节课，我们实现了数字员工团队的协作协议——共享工作区 + 邮箱机制。Manager 可以分配任务给 PM，PM 写完文档后回邮件通知，整个流水线自动流转。从架构上看，这已经是一个"自主运转"的团队了。

但有一个问题始终悬在空中：谁来告诉团队做什么？做完了谁来说对不对？出了问题谁来救场？

还记得我们在前面课程里提到的那个场景吗？——"我现在搞得神经衰弱，因为所有人都来问我，我变成了一根总线。"现在有了 Manager，你不再需要亲自串联每个 Agent——但你作为甲方，有三件事是绕不过去的。

本课就来解决这个问题：如何以工程化的方式设计人类介入点，让 Agent 团队在充分自主的前提下，把必须由人做的事留给人做。

一、认知原点：人类介入点的本质是什么？

人类介入点的本质，就是在 Agent 自主运行的流程中，提前标记出三个"人类必须在场"的环节——不是为了控制，而是为了让自主能够安全运转。

建立数字员工团队的目标，就是让它尽量自己干，减少人的介入。但"减少"不等于"没有"。

把自己想象成老板或甲方，而不是保姆。 保姆是中间帮他们串联——那事有 Manager 做了。甲方做什么？真正的老板和甲方做事情的时候，其实就三件事：第一，项目开始前把需求说清楚；第二，重要的方案过来拍板确认；第三，出了大问题出面处理。

这三件事，不是对员工能力的不信任，而是甲方职责的边界——它们缺了哪一件，团队都会出问题。需求没说清楚，后面所有工作方向都是错的；关键决策没有人拍板，风险在流程末端才暴露；系统崩了没人兜底，就会静悄悄地失控。

在 Agent 团队里，这三件事对应三个工程化的介入点：需求澄清（前端）、设计确认（中端）、异常兜底（后端）。这三个之外——Agent 完全自主，不打扰人。

这也是所有使用 Agent 产品的建议，不管你用的是什么框架——Agent 一旦自主运行起来，你的介入点就会比较薄弱。而且它一旦走错了路，你一开始没想清楚、它也没弄好，那基本上就是灾难：做出来的全都不是你想要的。所以这三个环节的设计至关重要。

二、为什么需要设计介入点：自主系统的三个失控场景

不设计介入点会怎样？我们来还原三个真实的失控场景。

场景一：需求没说清楚，方向偏了也不知道。

最常见的失控，发生在最开始。人发了一句话："帮我做个用户注册流程的产品设计。"听起来很清楚——但对 Agent 来说，歧义在哪里？邮箱注册还是手机号注册？要不要社交登录？邮件验证是否必须？

如果没有需求澄清环节，Agent 会按照自己的理解开始工作。Manager 分配任务给 PM，PM 写文档，Dev 开始开发——等到流程末端，人才发现："这不是我想要的。"

这时候的代价，不是重来一次——而是整个流水线反向退出，每一步的成本都浪费了。需求歧义是整个 Agent 系统的原罪：进去的是垃圾，出来的还是垃圾，只是更精致的垃圾。

场景二：没有确认点，关键风险在末端暴露。

假设需求是清楚的。Agent 团队开始工作：PM 写了产品文档，Dev 开始开发，QA 开始测试。整个流水线跑完，人看到最终结果——"等等，这个设计方案我不同意，应该这样做。"

想想看：如果你作为甲方，让团队干了 20 天，最终交付的东西不是你想要的，你肯定就毛了。最好的方式是：产品设计完成时——不是中间态，而是经过团队内部迭代的终稿——设一个 checkpoint，甲方过来看一下，"你们 PPT 写得不错，接着往下推进吧"。 研发阶段甲方可能看不懂，不管了——但上线前的验收又是一个 checkpoint。

没有中间确认点，等于把所有风险都堆到了末端——这和传统软件开发中"瀑布模型的失败"是同一个教训，只是在 Agent 系统里重新踩了一遍。

场景三：没有异常兜底，系统静悄悄失控。

Agent 系统在生产中必然会遇到自己无法处理的情况：工具调用连续失败、任务需求有歧义无法消解、准备执行的操作超出了预设的授权范围。假设某个 Agent 彻底挂了——就像某个程序员出了个车祸，项目要 delay——这时候如果没有通知到老板，Manager 一直在等，其他角色也不知道要干啥，整个任务就直接夯死了。

没有人在关键时刻接手，Agent 系统的"自主运行"会变成"自主失控"。

三、三个介入点的工程实现

💡 课程说明：本节代码已同步至 GitHub，地址：https://github.com/kid0317/crewai_mas_demo/blob/main/m4l27/

三个介入点分别对应三类工程机制。在设计上，有一条统一原则必须先说清楚。

3.0 单一接口原则（Single Point of Contact）

🧠 回忆一下：上节课的共享工作区里，每个角色都有自己的邮箱。那如果人类也需要和团队沟通，应该和哪个角色沟通？是 Manager？还是直接找 PM 确认文档？

答案是：人永远只和 Manager 沟通，不直接接触执行层。

本课代码中，human.json（人类专属邮箱）的写入权限只有 Manager 拥有——mailbox_cli.py 会强制校验：--to human --from pm 会直接返回 errcode=1。PM、Dev、QA 不能直接给人发消息。

为什么？因为 Manager 是任务全局上下文的持有者，执行层只有局部视角。如果 PM 可以直接给人发消息，SOP 里设计的确认机制就被绕开了；如果 Dev 直接向人汇报，人收到的是碎片化信息，不是可以决策的完整视图。这也符合实际业务——所有事都通过项目经理，你不用去跟底层的每一个执行者打交道。

所有人机交互经过 Manager，还有一个好处：完整的决策审计路径。出了问题，谁在什么时候基于什么信息做了什么决策，全部有据可查。

3.1 需求澄清：Manager 主动发问，落文档才算数

需求阶段，人只和 Manager 交流，Manager 主动发问——不是被动接收需求，而是像一个好的产品经理一样，拿到初步需求后主动追问模糊的地方。

本课引入了一个专属 Skill：requirements_discovery。Manager 调用这个 Skill 时，会按照四维框架主动发问：

  • 目标：这个任务成功的标准是什么？
  • 边界：哪些是必须做的？哪些明确不做？
  • 约束：时间、资源、技术有什么限制？
  • 风险：哪些决策需要提前确认？

你要指望一个人能把所有需求一次性提对，这几乎不可能。所以 Manager 需要有这样一套能力——根据初始需求，发现哪些维度写好了就不用澄清，哪些缺失就主动追问。经过几轮对话，产出一个更加明确的需求文档。

对话结束后，Manager 将需求写入 workspace/shared/needs/requirements.md，通过人类邮箱请人确认。没有确认的需求文档，Manager 不分配任何任务。

这条硬性门槛的意义在于：口头说了不算，写下来、确认了才算——签字画押的需求说明。它把"需求澄清"从一次性对话，变成了有可追溯记录的工程制品。

3.2 设计确认：SOP 中预埋 Checkpoint

需求确认后，任务不是靠 Manager"自我发挥"来协调的——必须有 SOP（标准作业流程）。

为什么要 SOP？因为如果是一个全新的团队，没有 SOP 的时候，遇到一个需求，应该谁干什么、每一步做哪些事，其实是不清楚的。所以在正式执行之前，你需要先跟 Manager 讨论好这套 SOP。

本课引入了 sop_creator Skill，让 Manager 与人共同设计 SOP 模板，包含四个要素：

  1. 角色分工：哪些角色参与，各自的职责边界
  1. 执行步骤：按顺序列出操作步骤，每步有明确的输入和输出
  1. Checkpoint：哪些环节需要人确认才能继续
  1. 质量标准：每个步骤的验收标准

Checkpoint 怎么设？ 不是越多越好。比如一个开发项目的 SOP：设计文档完成后——这不是中间态的草稿，而是经过团队内部迭代的终稿——设一个 checkpoint，甲方确认方向没问题再往下走。研发阶段甲方可能看不懂代码，不管了。测试完成后再设一个 checkpoint，汇报做了哪些功能、测试结果如何，甲方确认后上线。最终交付再做验收。

Checkpoint 的触发方式：Agent 完成这一步 → Manager 向 human.json 发邮件（type: checkpoint_request）等待确认 → 人通过 human_cli.py 回复确认 → Manager 检查确认状态后继续下一步。

Checkpoint 以外的所有步骤：Agent 完全自主，不打扰人。

谁来建 SOP？通常不是甲方——但你不光是甲方，你还是搭建这个数字员工团队的人。所以 SOP 还是要你事先跟 Manager 讨论好、建好的。Manager 的 sop_creator Skill 会引导你共同设计 SOP，确认后存入 SOP 模板库，后续项目通过 sop_selector Skill 选择匹配的 SOP。

3.3 异常兜底：出了问题，人来救场

第三个介入点是生产系统的最后一道门。Agent 系统在运行中会遇到三类需要人类介入的异常：

错误类：工具调用连续失败超过阈值（推荐 3 次），或多 Agent 协作中出现错误链式放大。

边界超出类：任务执行超时、Token 消耗超预算、Agent 准备执行超出授权范围的操作。这类要做熔断——而且熔断完了一定要把邮件发出来，否则人就很难发现问题。

质量边界：超过 3 轮优化仍无法达到质量标准；需求存在多种合理解释，Agent 无法独立选择；很多循环不收敛，实现过程中出现奇异的东西。

所有异常统一发送到 human.json，邮件包含四要素：异常类型 / 发生位置 / 当前状态 / 建议处理方式。人处理后回复 → Agent 收到后继续执行。极端情况下，人发送 stop 指令 → Manager 广播停止信号，所有 Agent 安全停止。

出错不可怕，怕的是出了错没人知道——人类邮箱就是这个团队的报警台。

四、代码实战：五步演示与 human_cli.py

💡 课程说明：本节代码已同步至 GitHub，路径：code/crewai_mas_demo/m4l27/

🧠 回忆一下：上节课我们用 DigitalWorkerCrew 框架让 Manager 和 PM 各自独立运行，通过 mailbox Skill 收发邮件——还记得吗？本课在那个框架上新增三类能力：需求澄清、SOP 管理、人类通知。

本课代码在第 26 课框架上新增了四个关键组件：

①requirements_discoverySkill（需求澄清）

Manager 专属 Skill，类型为 reference（参考型）——把四维发问框架注入 Manager 上下文，Manager 自己分析初始需求、识别缺失维度、整理澄清问题，最终写入 needs/requirements.md。

②sop_creator/sop_selectorSkill（SOP 管理）

sop_creator 引导 Manager 与人共同设计 SOP 模板（四要素框架），存入 shared/sop/；sop_selector 在正式项目中从模板库选出最匹配的 SOP，写入 active_sop.md。

③notify_humanSkill +human.json邮箱（通知人类）

所有需要人确认的节点，Manager 通过 notify_human Skill 向 human.json 发消息。消息类型有五种：

type用途
:----:----
needs_confirm需求文档待确认
sop_draft_confirmSOP 草稿待审阅
sop_confirmSOP 选择待确认
checkpoint_request阶段性交付物审核
error_alert异常上报

注意一个设计细节：human.json 使用二态（read: false/true），而不是 Agent 邮箱的三态。为什么？因为 Human 不是 Agent——不需要 in_progress 状态，也不需要崩溃恢复。Human 确认就是确认，拒绝就是拒绝（拒绝时还会有 rejected: true 和 human_feedback 字段）。

④human_cli.py（Human 端命令行工具）

这是本课的核心新增——一个独立的命令行工具，让 Human 在自己的终端异步操作，不阻塞 Manager。

# 交互式模式：循环检查消息，逐条回复
python human_cli.py

# 脚本模式：检查未读消息
python human_cli.py check

# 脚本模式：确认/拒绝指定消息
python human_cli.py respond <msg_id> y              # 确认
python human_cli.py respond <msg_id> n "修改意见"   # 拒绝+反馈

这跟上节课的设计哲学一致——Manager 完成当前能做的事就退出，不阻塞等人。Human 在自己方便的时候打开 human_cli.py 查看和回复。下次运行 main.py 时，Manager 检查 human.json 的 read 字段判断 Human 是否已确认。

完整演示：五步执行流程

课程为了方便理解和 debug，还是拆开给大家演示——Manager 和 PM 各自独立启动，Human 在独立终端通过 human_cli.py 异步确认。到第 29 课会以 XiaoPaw 为框架集成为常驻团队。

# === 步骤 1：Manager 初始化 + 需求澄清 ===
python main.py "帮我把用户注册流程的产品设计做出来"
# Manager 加载 init_project Skill → 创建工作区（含 human.json）
# Manager 加载 requirements_discovery Skill → 四维追问 → 写 requirements.md
# Manager 加载 notify_human Skill → 发 needs_confirm 给 Human → 退出

# === Human 确认需求 ===
python human_cli.py                # 交互式查看消息 → 确认(y)/拒绝(n)

# === 步骤 2：Manager 选择 SOP ===
python main.py "需求已确认，请选择 SOP 并分配任务"
# Manager 检查 human.json → 确认需求已读 → 加载 sop_selector → 选定 SOP
# Manager 发 sop_confirm 给 Human → 退出

# === Human 确认 SOP ===
python human_cli.py                # 确认 SOP 选择

# === 步骤 3：Manager 分配任务给 PM ===
python main.py "SOP 已确认，请向 PM 分配任务"
# Manager 加载 mailbox Skill → 发 task_assign 给 PM

# === 步骤 4：PM 执行任务 ===
python start_pm.py
# PM 检查邮箱 → 读需求 → 写产品文档 → 发 task_done 给 Manager

# === 步骤 5：Manager 验收 ===
python main.py "设计已确认，请审核产品文档"
# Manager 读 task_done → 读产品文档 → 写验收报告 → 标记消息 done

两个设计决策值得注意。

第一，Manager 不阻塞等人。每一步 Manager 完成当前能做的事就退出——发完需求确认邮件就退出、发完 SOP 确认就退出。Human 在任何时候打开 human_cli.py 确认。这跟上节课"同步通知 + 后台轮询"的理念一致：Manager 负责发通知，Human 异步处理。

第二，Agent 的汇报不能当真看。有时候 Agent 跟你交互的时候会说谎——不是恶意的，而是 Manager 的幻觉，或者它为了让你通过验收，会在邮件里写你想看到的。你在用任何 Agent 产品的时候都可能遇到这个——它明明那么做的，但它给你写的是你想要的。所以不要只看邮件里 Manager 写的"审查通过了，OK"——你还是要打开它让你审批的那个产品文档，真正看一看。

五、最佳实践与反模式

🚫 严重破坏稳定性的"反模式"

反模式一：审批疲劳（Approval Fatigue）

现象：Checkpoint 设得太多——每一步都问人"确认吗？"。刚开始你还认真看，后来就开始无脑点通过了。"你开始对它脱敏了"（Avani Desai，Schellman CEO）。

致命后果：高频确认让人失去判断力——真正需要确认的决策也被橡皮图章通过。Checkpoint 不是越多越好，设太多等于没有设。审批决策太多，你的决策质量反而变低了。

反模式二：人完全退出循环

现象：觉得"Agent 都能自主了，我不用管了"——让 Agent 完全自主运行，自己不再介入。

致命后果："Agent 完全自主"和"建立数字员工团队"是两件不同的事。没有甲方的项目没有边界，没有边界的自主是失控——Agent 做不受限的架构决策，代码库质量随时间持续劣化。大部分情况下，Agent 第一遍给的东西都通不了——不管你用什么产品都有这个问题，中间一定需要审批和反馈。

反模式三：无审计轨迹

现象：只存聊天记录，不存 tool call payload 和决策理由。所有的审批都没有日志落下来。

致命后果：出了事没有人知道谁批准了什么、什么时候、基于什么信息。"故障没有响声，只是悄悄污染了报表。"我们后面讲复盘的时候还会再讲——所有审批在 human.json 里面，中间的所有审批记录都要有据可查。

反模式四："谎言在循环中"（Lie in the Loop，LITL）

现象：Agent 汇报的内容与实际执行的不同——在邮件里写"已完成""审查通过"，但实际产出物并不符合要求。更极端的情况是攻击者在 prompt 中嵌入指令，审批对话框显示的内容与 Agent 实际执行的操作不同。

致命后果：人批准的是幻象，HITL 变成了攻击面而非防护层。你看到的和 Agent 实际执行的，可能不是同一件事——所以不要只看邮件里的文字，要去打开实际的产出物看一看。

💡 稳健落地的"最佳实践"

最佳实践一："在循环之上"（on the loop），不是"在循环之中"（in the loop）

落地心法：Martin Fowler 提出了这个区分——"in the loop = fix artifact. On the loop = fix the harness." 甲方的价值在于定义标准和设计流程（SOP），而不是审查每一行 Agent 的输出。SOP 设计好了，后续就会方便很多；SOP 没设计好，后面就废了。随着系统运行成熟，高置信度的决策可以自动批准，人的注意力集中在真正需要判断的地方。

最佳实践二：风险分级审批

落地心法：不是所有操作都需要人工确认。三级决策树：低风险 + 高置信度 → 自动执行，不设 checkpoint；中等风险 → 人工确认；高风险或低置信度 → 阻塞并路由给指定负责人。实践数据显示，合理的风险分级可以减少 60-80% 的无效审批，让真正重要的确认点获得足够注意力。

最佳实践三：完整审计日志，10 分钟内可重建任何事故

落地心法：日志包含：用户意图、检索文档 ID、模型版本 + 完整 prompt、tool call payload、最终操作结果、审批/拒绝决定及审核人身份。目标：任何事故 10 分钟内可完整重建。HITL 不只是"有人看了一眼"，要有据可查。

最佳实践四：全局停止开关 + 熔断器

落地心法：Agent 自主运行时，一定要有全局停止开关——Token 超了、工具调用次数太长、响应时间有问题，都要做熔断。而且熔断完了一定要把邮件发出来——否则人就很难发现问题并去解决。每个异常类型有指定负责人和响应时间 SLA，"No ownership for incidents"是已命名的反模式——不是没有人，是没有指定的人，等于没有人。

课程总结

  • 我们明确了人类在 Agent 团队中的角色定位——不是保姆，不是监工，而是甲方。甲方做三件事：说清需求、拍板确认、出问题兜底——这三件之外，团队完全自主。
  • 我们实现了三个介入点的工程化设计：需求澄清（Manager 主动四维追问 → 落文档 → 人确认才开工）、设计确认（SOP 中预埋 checkpoint → 邮件异步等待确认）、异常兜底（三类异常统一发 human.json → 人处理后继续或全员停止）。
  • 我们引入了 human_cli.py 异步确认机制——Manager 不阻塞等人，完成当前能做的事就退出；Human 在自己的终端独立操作。human.json 使用二态（read: false/true），与 Agent 邮箱的三态设计有意区分。
  • 单一接口原则贯穿始终：人永远只和 Manager 沟通，Manager 是人和团队之间唯一的接口。所有人机交互经过 Manager，保证完整的决策审计路径。
